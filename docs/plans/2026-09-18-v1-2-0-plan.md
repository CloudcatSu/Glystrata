## 1. 快照可寫註解

### 現況

- `SnapshotInfo`（`src/Glystrata.Core/Snapshots/SnapshotInfo.cs:11`）是 positional record，
  欄位為 `Id / CreatedUtc / Text / Encoding / LineEnding / SourceFingerprint`，沒有註解欄位。
- 磁碟格式是文件旁的 `<檔名>.gss`（JSON），由 `SnapshotSidecarStore` 整包讀寫。
- 快照紀錄視窗（`SnapshotHistoryWindow`）的清單是一行字串：
  `"2026-09-18 10:23:45  ·  12,345 chars"`（`SnapshotHistoryWindow.xaml.cs:88`）。

### 做法

**資料層**

1. `SnapshotInfo` 尾端加一個有預設值的 positional 參數 `string Note = ""`。
   有預設值就不會破壞現有所有建構點（`SnapshotService.CreateAsync`、`SnapshotEntry.ToInfo`）。
2. `SnapshotEntry` 加 `public string Note { get; set; } = ""`，`ToInfo` / `FromInfo` 一起帶。
3. sidecar 是純加欄位，**向前向後都相容**：舊檔沒有 `note` → 反序列化成 `""`；
   舊版程式讀到有 `note` 的檔會忽略它。`SchemaVersion` 維持 `1` 即可（程式目前也沒有讀它做分支）。
4. `ISnapshotService` 加一個方法：
   `Task<bool> UpdateNoteAsync(string sourcePath, Guid snapshotId, string note, CancellationToken ct = default)`
   實作是 read → 取代該筆 → write（跟 `DeleteAsync` 同一個模式）。
   - **注意**：這是 read-modify-write，`SnapshotTimer_Tick` 的自動快照可能同時寫同一個檔。
     現有 `DeleteAsync` 已經有一樣的競態，暫時沿用同一風險等級；若要保險，
     可在 `SnapshotSidecarStore` 內加一把 per-path 的 `SemaphoreSlim` 統一序列化所有寫入（建議順手做，成本很低）。

**UI 層（`SnapshotHistoryWindow`）**

5. 版面從「清單 + 按鈕列」改為三列：清單（`*`）／註解編輯區（`Auto`）／按鈕列（`Auto`）。
6. 清單每一筆改成兩行（用 `StackPanel` 當 `ListBoxItem.Content`）：
   - 第一行：時間 · 字元數（維持現狀）
   - 第二行：註解單行預覽，`SecondaryTextBrush`、`TextTrimming=CharacterEllipsis`；空註解就不顯示第二行
7. 註解編輯區：`TextBlock` 標籤（`snapshot.note`）+ 多行 `TextBox`
   （`AcceptsReturn=True`、`TextWrapping=Wrap`、高度約 70）。
   - 選到快照 → 載入該筆註解；沒選 → 停用並清空。
   - 存檔時機：**切換選取前**、**視窗關閉前**、以及焦點離開 `TextBox` 時，
     各自呼叫一次「若有變更就寫入」。這比加一顆「儲存註解」按鈕少一次點擊，
     但一定要在切換選取前先存，否則使用者打完字直接點下一筆會掉字。
   - 寫入成功後更新清單那一筆的預覽文字（不必整個 `RefreshAsync`，避免捲動位置跳掉）。
8. 「立即建立快照」**不**跳出輸入註解的對話框（依你的要求：預設留空白，想寫再到對話框寫）。

**在地化新增鍵**（`LocalizationService`，中英各一份）

```
snapshot.note            註解 / Note
snapshot.notePlaceholder 這個版本改了什麼？（選填） / What changed in this version? (optional)
```

### 會動到的檔案

- `src/Glystrata.Core/Snapshots/SnapshotInfo.cs`
- `src/Glystrata.Core/Snapshots/SnapshotService.cs`
- `src/Glystrata.Core/Snapshots/SnapshotSidecarStore.cs`（若加寫入序列化）
- `src/Glystrata/Views/SnapshotHistoryWindow.xaml` / `.xaml.cs`
- `src/Glystrata/Services/LocalizationService.cs`

### 風險

- 低。唯一要小心的是「切換選取時先存檔」的順序，寫錯會掉字。
- `DiffWindow` 的下拉選單也列出快照（`DiffWindow`），可順手把註解一起顯示在選項文字裡，
  不做也不影響功能。

## 2. 文件 TAB 右鍵選單加「立即建立快照」

### 現況

- 分頁右鍵選單在 `EditorPaneControl.CreateContextMenu()`（`src/Glystrata/Controls/EditorPaneControl.cs:370`），
  目前有：關閉 / Markdown 閱讀器 / 在資料夾中顯示 / 在新窗格開啟 / 移動到群組 / 快照紀錄 / 重新命名。
- `MainWindow.CreateSnapshotNow()`（`MainWindow.xaml.cs:1634`）只認 `ActiveView`，不吃參數。
- 在地化鍵 `file.createSnapshot` 已存在（「立即建立快照」），可直接重用。

### 做法

1. `EditorPaneControl` 新增事件 `public event EventHandler<DocumentViewState>? CreateSnapshotRequested;`
2. 在 `CreateContextMenu` 中、「快照紀錄」下面插入一個 `MenuItem`，`Header = _localization.Get("file.createSnapshot")`。
3. `MainWindow.CreateLayoutVisual` 裡接上：`pane.CreateSnapshotRequested += (_, view) => CreateSnapshotNow(view);`
4. `CreateSnapshotNow` 改簽章為 `CreateSnapshotNow(DocumentViewState? requestedView = null)`，
   內部照 `OpenSnapshotHistory` 的寫法 `var view = requestedView ?? ActiveView;`。
   選單列的「立即建立快照」呼叫端不用改。
5. 快照對話框上的按鈕維持原樣，不動。

**順手修掉的小問題**：右鍵選單是在 `AddView` 時建一次就固定了，
所以「在資料夾中顯示」的 `IsEnabled = FilePath is not null` 在「未命名分頁存檔後」不會更新。
新加的「立即建立快照」有一樣的狀況。建議改成在 `ContextMenuOpening` 時重算這兩項的 `IsEnabled`
（一行事件、影響範圍很小）。

### 會動到的檔案

- `src/Glystrata/Controls/EditorPaneControl.cs`
- `src/Glystrata/MainWindow.xaml.cs`

### 風險

無。

## 3. 全功能快捷鍵：建議怎麼設定

### 現況（問題所在）

快捷鍵現在有兩份互不相干的真相：

- **行為**：`MainWindow.Window_PreviewKeyDown`（`MainWindow.xaml.cs:242`）裡一段寫死的 `switch`。
  最上面還有一道門檻：修飾鍵**只接受** `Ctrl` 或 `Ctrl+Shift`，其餘（`F1`、`F3`、`Ctrl+Alt`、
  單鍵）一律直接 return。要加新快捷鍵一定得先改這個結構。
- **顯示**：`CreateMenuItem(key, action, gesture)` 的 `gesture` 是一個手寫字串
  （`MainWindow.xaml.cs:398`～）。選單顯示什麼、實際按下去做什麼，兩邊完全沒有連動，
  改一邊忘了另一邊就會不一致。

### 建議架構（三層，這是我的主要建議）

**(a) 一張命令表當唯一真相**

新增 `src/Glystrata/Input/AppCommand.cs`：

```csharp
public enum AppCommandId { FileNew, FileOpen, FileSave, ..., FormatBold, ViewSplitHorizontal, ... }

public sealed record AppCommandDefinition(
    AppCommandId Id,
    string LocalizationKey,   // 選單文字，沿用現有的鍵
    string? DefaultGesture);  // "Ctrl+Shift+S"；null = 沒有預設快捷鍵
```

`AppCommands.All` 是一個 `static readonly` 陣列，列出全部命令與預設鍵。

**(b) 一個服務負責解析與比對**

新增 `src/Glystrata/Input/ShortcutService.cs`：

- 用 `KeyGestureConverter` 把字串轉成 `KeyGesture`（免得自己解析字串出錯）。
- 對外只有兩個方法：
  - `string? GetGestureText(AppCommandId id)` → 給 `MenuItem.InputGestureText` 用
  - `AppCommandId? Resolve(KeyEventArgs e)` → 給 `PreviewKeyDown` 用
- 啟動時檢查是否有兩個命令綁到同一組鍵，有的話寫進 `errors.log` 並讓後者失效（不要靜默覆蓋）。

**(c) 兩個呼叫端都改成查這張表**

- `CreateMenuItem(AppCommandId id, Action action)`：文字與 gesture 都從表裡拿，
  再也不可能對不上。
- `Window_PreviewKeyDown` 整段換成：

```csharp
if (e.Key == Key.ImeProcessed) return;              // ← 必要：中文輸入法組字中不可攔截
if (_shortcuts.Resolve(e) is not { } id) return;
_dispatch[id](); e.Handled = true;
```

`_dispatch` 是 `Dictionary<AppCommandId, Action>`，在 `BuildMenu` 旁邊一次建好。

**(d) 可自訂與否 → 建議 v1.2.0 只做「架構 + 固定預設值」，自訂留到 1.3.0**

理由：自訂 UI（列表 + 錄製按鍵 + 衝突偵測 + 還原單項預設）本身就是一個完整的偏好設定分頁，
規模跟第 7 項差不多。但**資料結構先留好**：`AppSettings` 加
`public Dictionary<string, string> ShortcutOverrides { get; set; } = new();`
（命令 Id → gesture 字串，只存跟預設不同的項目）。
`ShortcutService` 啟動時套用 override，這樣以後補 UI 不用再改資料格式，
匯出設定檔（第 11 項）也自然涵蓋快捷鍵。

### 建議的預設鍵表

**避開的既有綁定**（AvalonEdit `TextArea` 內建，被窗層 `PreviewKeyDown` 攔走就等於廢掉）：

## 4. 調整視窗大小時偶爾閃爍

### 現況與嫌疑犯

這題**不要先寫修正，要先證明原因**——`docs/open-issues.md` 的附錄已經記過教訓：
WPF 的輸入／繪製問題靠靜態閱讀推測，連續兩次都猜錯。

目前看得到的三個嫌疑點：

1. **自訂標題列 + WindowChrome**（`src/Glystrata/Controls/CustomTitleBar.cs:61`）
   `GlassFrameThickness = (0,0,0,1)` 會把 DWM frame 延伸進 client area，
   Win11 上那塊 frame 是純黑。拖曳邊框時 Win32 先 blit／擦背景、WPF 才交出新的一幀，
   中間那個空檔就是黑色閃一下。`ApplyCompositionBackground`（`:237`）已經處理了「首次顯示」的版本，
   但**沒有處理 `WM_ERASEBKGND`**。
2. **AvalonEdit 自動換行的重新量測**：編輯器固定 `WordWrap = true`
   （`EditorPaneControl.cs:250`）。寬度一變，所有可見行都要重新斷行量測。
   這跟 `docs/open-issues.md` 第 1 項（捲軸拖曳卡頓）根源可能是同一個。
   佈局慢 → 上面那個空檔變長 → 閃爍從「看不到」變成「看得到」。
3. **側邊欄 `GridSplitter` + `TreeView`**：可能性最低，但拖曳側邊欄分隔線時也會觸發同一條路徑，
   正好可以拿來當對照組。

### 診斷計畫（先做這個）

| 步驟 | 要回答的問題 |
|---|---|
| A | 閃的是**黑色**還是**視窗底色**？黑 → 1（DWM frame）；底色 → 2（WPF 重新佈局來不及） |
| B | 哪一邊在閃？右／下邊 vs 左／上邊。拉左／上邊時 Win32 是整塊搬移，症狀通常更明顯 |
| C | **關掉所有分頁**（空窗格）再拉大小，還閃嗎？還閃 → 排除 2，鎖定 1 |
| D | 暫時把 `WordWrap` 設成 `false` 重編一版再拉，症狀消失 → 就是 2 |
| E | 只拖側邊欄 `GridSplitter`（視窗大小不變）會閃嗎？會 → 是佈局成本，不是視窗框 |

C、D、E 都不需要寫新程式，改一行重編就能跑，先花 20 分鐘把範圍縮到一個原因再動手。

### 依診斷結果的候選修正

- **若是 1（DWM frame）**：在 `CustomTitleBar.WndProc` 加 `WM_ERASEBKGND` → 回傳 1（表示已處理，
  不要讓 Win32 用系統筆刷擦背景）。這是 WindowChrome 應用最常見也最有效的一招。
  次要選項：在 `WM_ENTERSIZEMOVE` / `WM_EXITSIZEMOVE` 之間暫停某些重繪。
  現成的 HwndSource hook 已經在那裡了（`:225`），不必新開一個。
- **若是 2（換行量測）**：拖曳期間（`WM_ENTERSIZEMOVE`～`WM_EXITSIZEMOVE`）先把
  非作用中分頁的編輯器 `Visibility` 設成 `Hidden`，結束再還原；或評估把
  `TextView` 的量測改成延遲。**這是動到核心捲動／排版行為，風險等級等同 open-issues 第 2 項，
  不要當小調整處理。**
- **若是 3**：`GridSplitter.ShowsPreview = true`（拖曳時只畫預覽線，放開才重排）。

### 風險

- 中～高，取決於落在哪一類。無論哪一種都**必須實機驗證**，不能只靠單元測試。
- 可能與 open-issues 第 1 項（捲軸拖曳卡頓）同源；若真的是換行量測，建議兩題一起處理，
  但也要一起承擔「可能弄壞游標定位與選取繪製」的風險。

## 5. 「檔案」→「最近開啟過的文件」

### 現況

完全沒有這個概念。開檔路徑有四個入口，全部要記錄：

- `OpenFiles()`（`MainWindow.xaml.cs:1315`）→ 檔案對話框
- `OpenPath()`（`:1335`）→ 共用入口
- `Window_PreviewDrop`（`:134`）→ 拖放
- `OpenExternalPaths()`（`:185`）→ 第二個執行個體轉交進來的檔案
- 另外 `SaveActiveAsAsync()` 另存新檔後也該記一筆

### 做法

**儲存位置：獨立的 `recent.json`，不要放進 `settings.json`**

理由：第 11 項要匯出／匯入設定檔。把「最近開啟的文件」塞進設定檔，
會讓匯出的檔案夾帶使用者的檔案路徑（隱私），匯入到另一台機器也全是失效路徑。

1. 新增 `src/Glystrata.Core/Persistence/RecentFilesState.cs`：

```csharp
public sealed class RecentFilesState
{
    public int SchemaVersion { get; set; } = 1;
    public List<RecentFileEntry> Files { get; set; } = new();
}
public sealed class RecentFileEntry
{
    public string Path { get; set; } = string.Empty;
    public DateTime LastOpenedUtc { get; set; }
}
```

2. `JsonStateStore` 加 `LoadRecentFilesAsync` / `SaveRecentFilesAsync`（沿用現有的 `LoadAsync`/`SaveAsync` 泛型），

## 6. 群組「加入檔案」改名為「開啟檔案」

### 現況（這裡有一個你可能要一併決定的問題）

`group.addFile`（「加入檔案…」）出現在三個地方：
選單列「群組」（`MainWindow.xaml.cs:424`）、群組右鍵選單（`:918`）、檔案對話框標題（`:1902`）。

三處都導向 `AddFilesToGroup()`（`:1895`），它做的事情是：

```csharp
foreach (var path in dialog.FileNames)
    _groups.AddPath(group.Id, path, GroupItemKind.File);   // 只寫進 groups.json
RebuildGroupsTree();
```

**它不會開啟任何分頁**。而且 `RebuildGroupsTree()`（`:753`）只為每個「群組」建一個節點，
**完全沒有列出群組底下的檔案項目**。分頁屬於哪個群組是靠 `DocumentViewState.SourceGroupId`
決定的，跟 `Group.Items` 是兩套獨立資料。

也就是說：現在按「加入檔案」，畫面上**什麼都不會發生**，只有 `groups.json` 默默多了幾行。

### 做法

**純改名（你原本要求的）**：只動在地化字串的「值」：

```
group.addFile: 加入檔案…  →  開啟檔案…
               Add files… →  Open files…
```

建議連鍵名也改成 `group.openFile`（3 個使用點，改動很小），免得日後看到鍵名叫 addFile 卻顯示「開啟檔案」而困惑。

**但請看決策 A**：改名成「開啟檔案」之後，使用者按下去卻沒有任何檔案被開啟，
體驗會比現在更糟（現在叫「加入檔案」至少不承諾會開啟）。
建議同時讓它真的開檔——實作只是在迴圈裡多一行：

```csharp
_groups.AddPath(group.Id, path, GroupItemKind.File);
OpenPath(path, group.Id, selectGroup: false);   // ← 新增這行，跟拖放的處理方式一致
```

`Window_PreviewDrop`（`:151`）已經是這樣做的，所以行為會變得一致，不是新發明。

## 8. 群組選取時的底色

### 現況

- 「全部 TAB」是一顆獨立的 `Button`（`MainWindow.xaml.cs:672`），選取時把
  `Background` 換成 `TabActiveBrush`（`RefreshAllTabsFilter`，`:837`）。
- 群組節點是 `TreeViewItem`，而主題字典裡的 `TreeViewItem` 樣板**明確把選取狀態的底色設成透明**：
  `Resources/Themes/Light.xaml:697`（Dark 同行號）

```xml
<Trigger Property="IsSelected" Value="True">
    <Setter TargetName="ItemBorder" Property="Background" Value="Transparent" />
```

所以目前群組被選到完全沒有視覺回饋（只有那顆小 `Ellipse` 亮起來）。

### 做法

1. **改樣板**：把上面那個 `Background = Transparent` 的 `Setter` 拿掉（Light / Dark 兩份都要），
   讓 `{TemplateBinding Background}` 透出來，這樣就能從程式碼逐一指定每個節點的底色。
   下面那個 hover 的 `MultiTrigger` 條件是 `IsSelected == False`，不受影響，不用動。
2. **算底色**：底色 = 群組顏色與側邊欄底色的混合。

```csharp
// 亮色主題 12%，暗色主題 24%（暗底需要更高比例才看得出來）
static Color Blend(Color accent, Color background, double ratio) => Color.FromRgb(
    (byte)(accent.R * ratio + background.R * (1 - ratio)), … );
```

   - 沒有指定顏色的群組 → 回退成現有的 `TabActiveBrush`（跟「所有文件」一致）。
   - 混合比例放在 `AppSettings`：`public double GroupSelectionTint { get; set; } = 0.12;`
     偏好設定「群組顏色」分頁底下加一條 0～50% 的滑桿 + 即時預覽列。
     這就是你說的「一樣在偏好設定裡面做管理」，而且只需要一個數字，
     不用讓使用者為每個顏色各挑兩次色。
3. **套用**：`RefreshGroupSelectionIndicators()`（`:851`）改成同時設定每個 `TreeViewItem.Background`
   （選中 → 混色筆刷；未選中 → `Brushes.Transparent`）。
4. **「所有文件」那顆按鈕**同步用同一套邏輯（它沒有群組顏色，維持 `TabActiveBrush`），
   這樣兩者的選取外觀才會一致。

## 10. 主題新增「跟隨系統」並設為預設

### 現況

- `ThemeKind { Light, Dark }`（`AppSettings.cs:9`），`AppSettings.Theme` 預設 `Light`。
- 這個 enum **同時扮演兩個角色**：使用者的偏好，以及「現在要套哪一組色盤」。
  程式裡有 **14 處**寫著 `xxx.Theme == ThemeKind.Dark ? 暗 : 亮`，分布在
  `MainWindow`、`SettingsWindow`（7 處）、`PreviewWindow`、`WpfMarkdownRenderer`、
  `MarkdownHelpWindow`、`ThemeService`。

### 做法

**(a) 把「偏好」和「實際生效」拆成兩個型別**

```csharp
public enum ThemePreference { System, Light, Dark }   // 使用者設定（AppSettings.Theme）
public enum ThemeKind       { Light, Dark }           // 實際生效（ThemeService.CurrentTheme）
```

`ThemeKind` 名字不變，所有「拿色盤」的程式碼繼續用它，只是來源從 `_settings.Theme`
改成 `_theme.CurrentTheme`。這樣 14 個使用點只要改「從哪裡拿」，不用改判斷邏輯。

**(b) 偵測系統主題**

讀登錄檔：
`HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\AppsUseLightTheme`
（DWORD，`0` = 暗色，`1` 或不存在 = 亮色）。

**即時跟隨**（使用者在 Windows 設定裡切換時立刻變）：
不要引入 `Microsoft.Win32.SystemEvents` 相依，改用**已經存在**的 HwndSource hook
（`CustomTitleBar.WndProc`，`:273`）攔 `WM_SETTINGCHANGE (0x001A)`，
`lParam` 字串等於 `"ImmersiveColorSet"` 時重讀登錄檔。零新相依、零輪詢。

建議把偵測抽成 `src/Glystrata/Services/SystemThemeWatcher.cs`，
對外只有 `ThemeKind Current` 與 `event EventHandler? Changed`，
讓 `CustomTitleBar` 只負責把訊息轉發過去（標題列不該懂主題邏輯）。

**(c) `ThemeService` 改造**

```csharp
public void Apply(ThemePreference preference)   // 解析 System → 實際 ThemeKind 後套用字典
public ThemeKind CurrentTheme { get; private set; }
```
系統主題變更事件 → 若目前偏好是 `System` 就重新 `Apply`，觸發既有的 `ThemeChanged`
（`MainWindow.Theme_ThemeChanged`，`:1947` 已經會刷新編輯器顏色、閱讀器、側邊欄，路徑是現成的）。

**(d) 偏好設定的連帶改動（重要）**

`_themeBox` 加第三個選項「跟隨系統」放在最前面（索引 0/1/2 = 系統/亮/暗）。

但現在「要編輯哪一組色盤」是綁在 `_working.Theme` 上的
（`SettingsWindow.xaml.cs:260`、`:281`、`:339`、`:350`）——選「跟隨系統」之後這個綁定就沒有意義了。

**建議一併改掉**：在「編輯器選項」與「閱讀器選項」兩個分頁最上面各加一組
「亮色 / 暗色」切換（`RadioButton` 或兩顆 `ToggleButton`），跟主題偏好**完全獨立**。
好處不只是解決這個問題——現在要編暗色色盤必須先把主題切成暗色，很不直覺。

**(e) 預設值與相容性**

- `AppSettings.Theme` 的預設值改成 `ThemePreference.System`。
- 既有使用者的 `settings.json` 已經寫著 `"theme": "Light"` 或 `"Dark"`，
  反序列化後維持原值 → **舊使用者保留自己的明確選擇，只有全新安裝才跟隨系統**。這是對的行為。
- `Normalize()` 要加 `if (!Enum.IsDefined(Theme)) Theme = ThemePreference.System;`
- 「還原預設」按鈕會把主題設回「跟隨系統」，這是預期行為。

- 序列化選項要跟 `JsonStateStore` 一致（camelCase、`WriteIndented`），
  這樣匯出檔跟 `settings.json` 長得一樣，好肉眼比對。

**⚠ 副檔名衝突**：`.gss` 目前是**快照 sidecar** 的副檔名
（`SnapshotSidecarStore.GetSidecarPath`），而且 `SnapshotFileAssociation` 已經幫它註冊了
檔案總管圖示。查過註冊內容（`SnapshotFileAssociation.cs:50`）：只寫了 `DefaultIcon`，
**沒有註冊 open 動詞**，所以雙擊不會啟動 Glystrata，功能上不會壞掉——
但匯出的設定檔會頂著「快照」的圖示，而且使用者可能誤把 sidecar 拿去匯入。

因此匯出的 JSON 最上面要加一個識別欄位：

```json
{
  "kind": "glystrata-settings",
  "schemaVersion": 1,
  "language": "TraditionalChinese",
  ...
}
```

匯入時檢查 `kind`；不符（例如拿到 sidecar，它的特徵是有 `notice` 與 `snapshots`）就明確報錯：
「這是快照檔案，不是設定檔。」

**(c) 匯入**

- `OpenFileDialog`，同樣的 filter。
- 讀檔 → 反序列化（`PropertyNameCaseInsensitive`、`AllowTrailingCommas`，與 `JsonStateStore` 相同）
  → 檢查 `kind` → 檢查 `schemaVersion` 不得大於本版支援值（未來版本的檔案要擋下來，
  而不是默默丟掉不認得的欄位）→ `Normalize()`。
- **匯入後不直接套用**：`CopySettings(imported, _working); LoadFields();`
  讓值填進對話框，使用者再按「套用」。這樣按「取消」還能反悔，比直接生效安全。
  匯入成功後在對話框內顯示一行提示（或用 `MessageDialogs.Inform`）。
- 匯入失敗一律吃掉例外（`JsonException` / `IOException` / `UnauthorizedAccessException`），
  顯示訊息，不要讓對話框炸掉。

**(d) `CopySettings` / `CloneSettings` 要補齊新欄位**

這兩個方法（`SettingsWindow.xaml.cs:473`、`:506`）是逐欄位手抄的，
第 3、7、8、10 項新增的欄位（`ShortcutOverrides`、`GroupColors`、`GroupSelectionTint`、
`Theme` 型別改變）**全部都要記得加進去**，漏掉會表現成「匯入後某些設定沒變」這種很難查的 bug。

> 建議順手改善：把 `CloneSettings` 改成 JSON round-trip
> （`JsonSerializer.Deserialize<AppSettings>(JsonSerializer.Serialize(source))`），
> 以後新增欄位就再也不會漏。效能完全不是問題（一個視窗開一次）。

**(e) 匯出的內容範圍**

包含整個 `AppSettings`：語言、主題、兩組編輯器色盤、兩組閱讀器色盤、閱讀器排版、
快照設定、字元計數模式、快捷列開關、群組色票、快捷鍵覆寫。

**不包含**：`groups.json`（群組與成員）、`session.json`（開啟的分頁與版面）、
`recent.json`（最近開啟的文件）。這些是「這台機器的工作狀態」，不是「偏好」。
若之後想要「連工作區一起搬」，那是另一個功能（匯出工作區），不要混進來。

## 需要你先決定的事項

### 決策 A — 群組的「開啟檔案」要不要真的開檔？（第 6 項）

現在的「加入檔案」按下去畫面毫無反應（只寫進 `groups.json`，而群組節點根本不列出檔案）。
改名成「開啟檔案」之後這個落差會更明顯。

1. **只改名**（照你原本說的）——按下去仍然什麼都不會發生
2. **改名 + 真的開檔**（建議）——多一行 `OpenPath(path, group.Id, selectGroup: false)`，
   跟拖放檔案進來的行為一致

### 決策 B — 群組顏色存「色票 Id」還是「色碼」？（第 7 項）

1. **存色票 Id**（建議）——在偏好設定調色，所有使用該色票的群組同步變色；
   代價是刪除色票要處理指向失效的群組
2. **存色碼**——沒有失效問題，但偏好設定改色不會影響已指定的群組，
   「管理色盤」就只是個挑色器而已

### 決策 C — 選取指示點（小圓點）要保留嗎？（第 7、8 項）

第 8 項做完之後，被選取的群組會有底色，那顆 `Ellipse` 就是重複的資訊。

1. **保留**（預設）——兩種指示並存
2. **拿掉**——側邊欄更乾淨，直槓（群組色）+ 底色（選取）各司其職

### 決策 D — 快捷鍵這一版做到哪裡？（第 3 項）

1. **架構 + 固定預設鍵**（建議）——本版把命令表、解析服務、選單連動做好，
   資料結構預留 `ShortcutOverrides`；使用者不能自訂
2. **連自訂 UI 一起做**——多一個偏好設定分頁（列表 + 錄製按鍵 + 衝突偵測 + 單項還原），
   規模大約等於第 7 項，1.2.0 會變得相當肥

### 決策 E — `Ctrl+I` 給斜體嗎？（第 3 項）

`Ctrl+I` 是 AvalonEdit 內建的「縮排選取範圍」。給了斜體就等於拿掉它（縮排還有 Tab 可用）。

1. **給斜體**（建議，符合一般文書軟體直覺）
2. **改用 `Ctrl+Shift+I`**，保留 AvalonEdit 的縮排
